# 通知中的名称与编码

飞书卡片在主体显示“编码 · 名称”，完整 Run、Batch、Feature、Task UUID 放在底部排查信息中。旧通知或无法关联名称的事件继续显示原 ID，不猜测归属。

| 对象 | 显示编码示例 | 编号范围 |
| --- | --- | --- |
| Phase | `P01` | 项目内 |
| Feature | `P01-F02` | Phase 内 |
| 编码 Task | `P01-F02-T001` | Feature 内 |
| Planner Task | `P01-F02-PLAN` | 所属 Feature 的规划操作，多次规划共用此显示别名 |

编码是持久化显示别名，UUID 仍是正式接口、CLI 参数和关联查询的身份。编码不参与计划摘要、批准或 CAS。

迁移 v69 按创建时间分配历史编号，同一时间按原始插入顺序分配；不会解析标题中的 P/F/T 字样。新对象在创建事务中自动分配。标题、列表排序、DAG 调整不改变已有编号；删除并替换任务会保留旧编号占位，新增任务取下一号，同一对象 ID 恢复时沿用原号。显示编号不保证连续，也不代表执行顺序。

`entity_display_codes` 由 Core 的版本化迁移和创建触发器维护，项目删除清点包含此表。通知投影仅做同项目元数据查询，不扫描会话。名称、编码、语言和统计写入原有持久通知队列；重试或水位回放沿用原快照，不因改名产生摘要冲突。已发送的历史飞书消息不会被改写或重发。

规划任务成功的卡片标题为“规划完成，等待批准”（英文为 `Plan ready for approval`）；它不表示候选已批准或编码任务已通过验收。失败和限流仍保留原来的失败分类、开关和颜色。

## 升级兼容性

本次迁移前的自动备份暴露两处历史兼容问题，已修复：备份缺口原因允许与写入器一致的有界冒号命名空间（如 `recording_failed:aborted`）；启动升级的回滚快照可以原样保留历史录制缺口，不要求补造已经丢失的录制事件。备份校验报告仍明确显示录制不完整，普通备份/恢复验收仍保持严格检查。升级只允许这一项历史缺口，其余 SQLite 完整性、制品、引用、原生归档等检查仍必须通过，升级前后仍核对全部进程停止证据。
