## 2. 三层验证必须区分

| 层次 | 命令 | 用途 |
|---|---|---|
| 开发测试 | `npm test` | 原有 Vitest 测试，其中既有单元测试也有真实集成测试，不应统称单元测试 |
| 原阶段门禁 | `npm run verify`、`npm run accept:p01` | 原有完整检查、四组场景和报告门禁；会运行 Vitest |
| 本次独立集成 | `node scripts/acceptance/run-p01.mjs --offline` | 新的纯 Node 脚本；直接调用构建后的公共 Core；不调用 Vitest、`npm test` 或 LLM |

新脚本不替代原门禁，原门禁也不替代人工审阅。所有检查必须真执行；失败、超时、漏项都不算通过。

## 3. 操作步骤

在 `acceptance/p01` 的 checkout/worktree 中使用 `.nvmrc` 锁定的 Node 22.19.0、npm 10.9.3。

```bash
nvm use
npm ci --offline --no-audit --no-fund
npm run verify
npm run accept:p01
node scripts/acceptance/run-p01.mjs --offline
```

- 缓存不完整时去掉安装命令及独立脚本的 `--offline`，只允许依赖安装访问 npm；业务集成场景无需网络、登录或模型 Key。
- 独立脚本默认测当前仓库 `HEAD` 的已提交版本；未提交业务修复不会进入克隆快照。先提交修复，或明确指定其他已提交 `--ref`。
- 可指定 `--repo <本地仓库>`、`--ref <分支或commit>`、`--out <报告根>`。
- 独立脚本创建临时 clone 并安装、构建；在两个互相隔离的临时数据根各运行 12 项检查，验证可重复性。
- 报告在 `artifacts/acceptance/p01-integration/<run-id>/`，含 `report.json`、`summary.md`、步骤日志、两轮逐项结果。
- 每步有有限超时；子进程非零、缺工具、场景缺失均整体失败。CAS 工作者会超时终止，不无界等待。
- 报告先写出，临时目录保留供排障。只对明确属于本次脚本的临时目录手动清理，绝不删除源仓库。
- 脚本输出临时路径方便本机排障，报告不包含真实认证信息；分享报告前仍检查路径和隐私。

## 4. 独立集成场景

| ID | 场景 | 核验结果与副作用 |
|---|---|---|
| I01 | 两个真实 Git 仓库注册、重复注册 | 稳定 projectId、规范路径、重复注册不覆盖元数据、不同仓库身份不同 |
| I02 | 全局配置与项目覆盖 | 完整策略替换、来源为项目、配置合法不代表模型已就绪 |
| I03 | 未注册 runtime 的非法更新 | 拒绝且当前配置、revision 不变 |
| I04 | UTF-8 制品发布和读取 | 实际正文、SHA-256、ready 状态一致 |
| I05 | 新 Node 进程重开 | 项目、配置、有效来源逐字段一致，制品正文/hash/size 一致 |
| I06 | 两个独立进程同时更新同 revision | 恰一个成功、一个 conflict，revision 只增加一次，实际持久值一致 |
| I07 | 项目标签筛选和计数 | 标签规范化、筛选正确、重复标签只计一次 |
| I08 | 用另一个 projectId 读制品 | 明确拒绝，原项目仍能读出原正文 |
| I09 | 篡改正文、恢复字节 | 篡改不能有效读取，恢复后重新核验通过；不宣称自动灾备恢复 |
| I10 | 删除正文、补回原字节 | 缺失明确失败，不伪装为空内容；补回后核验通过 |
| I11 | 注册/配置/制品操作后的源仓库 | HEAD、refs、Git status、根文件清单与哨兵正文均不变 |
| I12 | SQLite trigger 注入审计写入错误 | 公共 ProjectService 更新拒绝、业务值与 revision 回滚、审计数量不变、重开仍为旧值 |

I12 仅对脚本自己的数据库安装故障 trigger，不直接插业务行；实际写入仍经公共应用服务。
I06 通过 ready/go 文件屏障同时释放两个真实 Node 进程，非顺序陈旧 revision 冒充竞争。
