# Core · application

应用层：命令、查询与执行编排（用例服务、调度、预算、验收编排）。

- 允许：依赖 `domain` 与 `ports` 中声明的窄接口；以显式调用组织用例；依赖注入在边界装配。
- 禁止：依赖具体适配器实现（`adapters/*`）；导入或重导出 Pi SDK、Electron、HTTP 框架、`better-sqlite3`、Drizzle；直接发起网络监听或持有用户数据路径之外的写入；空壳的项目/调度/存储/Runtime 服务。

当前阶段（P01-2 / F-011、F-012）：`artifact-publish.ts` 为首个用例服务——制品流式发布编排（pending 登记 → 事务外 staging 流式写入与同步 → hash 核验 → 同文件系统不覆盖发布 → 短事务 CAS ready），只依赖 `ports` 的 ArtifactStore/ArtifactFileStore 窄接口与 node 内置模块；限制（大小/时间/取消）显式有限，失败保留阶段化证据与 staging 残留。`artifact-verify.ts`（F-012）为制品中断核对与损坏诊断用例：关闭重开后的 pending 恢复（正式文件核验通过后 CAS 补 ready，冲突时按 revision 重新核对、不让旧结果倒写）、ready 完整性核对与三种 corrupt 诊断（missing/size_mismatch/hash_mismatch）、必要完整性检查的有效读取（缓冲受显式上限约束）与项目级批量核对/孤儿扫描（原文件保留 kept_in_place，不制造索引、不删除未知文件）。其余用例实现从后续 Feature 开始按设计 `core-design/04-scheduling-and-recovery.md` 等进入。

P01-3 / F-005 起新增 `project-service.ts`：ProjectService 仓库注册用例（registerRepository）——输入运行时校验（元数据复用 F-002 共用校验器，非法输入先于任何 I/O 拒绝）→ 只读仓库检查（RepositoryInspector，数据库写事务之外）→ 单个短事务原子保存项目 + 绑定（StateStore.createProjectWithRepositoryBinding，同 canonicalPath 幂等复用返回 already_exists，不同 clone 分别注册）。只依赖 ports 窄接口，不接触适配器/驱动/HTTP/Pi SDK。

P01-3 / F-006 起同一 `project-service.ts` 补充：`getProject` / `getRepositoryBinding`（按 projectId 查询身份与完整绑定，未知 ID 为 not_found）与 `updateProjectMetadata`（名称/描述/标签 CAS 编辑，先经 F-002 共用校验器拒绝非法字段/标签，再交 `StateStore.updateProject` 在同一短事务内完成 CAS 更新与 `state_events` 脱敏变更记录）。改元数据不触碰 projectId、canonicalPath、配置、PathService 位置或已有制品。

P01-3 / F-007 起同一 `project-service.ts` 补充 `listProjects` / `countProjectLabels` 只读查询，直接复用 `StateStore.listProjects` / `StateStore.countProjectLabels`（任一/全部标签筛选、稳定 `id` 升序键集分页、项目层去重计数）；应用层不另立第二套标签规则，不实现按标签启动 Batch 或 Phase/Feature/Task 标签查询。

P01-3 / F-009 起新增 `effective-settings.ts`：全局默认与项目当前覆盖的**有效配置合并纯函数** `mergeEffectiveSettings`——键级继承、完整策略条目整体替换（不跨来源拼接 runtime/provider/model）、政策段级整体覆盖（段内不跨来源继承、数组整体替换、空段 `{}` 继承全局）、逐项来源解释（`global_default`/`project_default` + `sourceKey` + 来源 scope revision）。输入边界为 `unknown`：两个来源的 payload 合并前重新经 `validateSettingsPayload`（schemaVersion=2）校验，未知版本/未知键/不完整条目/非法政策带字段定位拒绝，不静默降级；双方均无策略时返回 `configured:false` 的明确未配置结果，不注入默认 Claude/API。纯函数：不修改原始 payload、不解析凭据引用、不创建 Task、不写执行快照；只依赖 ports。从 StateStore 组装来源输入的查询服务由 F-011 交付。

P01-3 / F-010 起新增 `configuration-service.ts`：ConfigurationService 命令切片（`createSettings` insert-only / `updateSettings` expectedRevision CAS）——严格顺序为 scope/输入运行时校验（先于任何 I/O，写入端口不被调用）→（project scope）读取全局当前配置作为一致性视图来源 → F-009 合并校验 + 合并后策略集合的能力兼容复检（F-008 目录，继承条目随当前目录复检）→ 存储端口条件写入；读取到的全局 revision 作为 `consistency.globalRevision` 前置条件随写入传入（调用方不得自行声明该键），与默认更新竞争时返回 conflict（stale_dependency），不提交基于陈旧依赖校验过的结果。成功的 CAS 更新由存储端口同事务追加 `settings.global_updated`/`settings.project_updated` 脱敏审计记录（`settingsChangeSummary` 摘要，不含值/引用/秘密）；首次创建不写审计记录。scope 即唯一目标身份渠道（项目 A 范围不能更新项目 B）；事务内只有 SQL，不进行网络/Git/模型/凭据解析。

P01-3 / F-011 起同一 `configuration-service.ts` 补充只读查询切片：`getCurrentSettings(scope)`（按 scope 返回 schemaVersion/已校验 payload/revision；缺失 not_found、损坏 corrupt、非法 scope 先于 I/O 拒绝）、`getEffectiveSettings(projectId)`（`getProject` 核验项目存在 → 读取全局/项目当前记录 → F-009 `mergeEffectiveSettings` 返回精确合并值与逐项来源；未知项目 not_found、双方均无策略 configured:false）与 `exportSettings(projectId?)`（`ExportedSettings`：`SETTINGS_EXPORT_FORMAT_VERSION` + scope 元数据 + 当前值逐字段白名单投影 + 有效配置来源；`credentialRef`/`endpointRef` 只保留引用字符串、不解析；缺失 not_found、未知版本/损坏 corrupt、不含 executable/ready 标记）。查询只经 StateStore 只读端口，不调用写入端口、不读环境/认证文件/Keychain/CredentialProvider、不导入 Pi SDK、不绑定 YAML 监听或 Host/CLI 路由。

P02-2 / F-006 起新增 `command-receipts-service.ts`：CommandReceiptsService 授权回执读取与结果引用解析（契约 §4.3/§5.6）——`getReceipt`（receipts.read 能力先于数据库读取；按调用方自身 principalId 查询，跨身份结构性 not_found；项目/注册回执目标当前可见性重核，不可见一律 not_found）与 `resolveResult`（非法 resultRef 形态字段级 invalid_input；未知/伪造/无权引用一律 not_found；返回提交时固化的 result，项目后续修改不改变该次结果）。注册回执的新建项目身份自固化结果提取，形状不符即 corrupt_state，不跳过可见性核验。只依赖 ports 窄接口，不接触适配器/HTTP；principal 由可信装配显式传入。

P02-2 / F-007 起新增 `command-service.ts`：`CommandService.submit(principal, unknown)` 复用信封/摘要/授权/时效纯契约；事务外预读用于过期新命令拒绝，权威回执重读、当前授权、时效、项目存在性与 CAS 再核验、业务写入/事件/完成回执均在同一同步事务。CAS 不匹配在任何业务写入前固化 rejected；写后错误一律整组回滚，不捕获成业务拒绝。completed/rejected 重放稳定，result 中项目/绑定时间为 ISO UTC；busy 明确 resource_busy。F-008 起接入 `project.register`：只读仓库检查（装配传入的 RepositoryInspector）在写事务之外、仅对新命令执行，事务内写「项目 + 绑定 + `project.registered` 创建事件 + completed 回执」；同 canonicalPath 命中返回 already_exists（不写事件、不覆盖名称/标签），命中不可见项目按 forbidden 拒绝且不积回执；注册重放重核当前可见性。F-009 起接入 `settings.global.create/update` 与 `settings.project.create/update`：能力目录复检与一致性视图（全局当前配置快照）在写事务之外、仅对新命令执行——全局 payload 直接复检，项目覆盖以「全局快照 + 新 payload」经 `validateMergedProjectSettingsWrite`（与 P01 ConfigurationService 同一合并校验纯函数）复检，继承条目随当前目录复检；推导出的 `consistency.globalRevision` 随写入在同一事务内核对，陈旧依赖固化 rejected stale_dependency。创建成功同事务写 `settings.*_created` 创建事件（仅命令路径，P01 直接服务首建不写），更新复用 P01 既有 `*_updated` 写入；重复创建固化 rejected already_exists，更新目标缺失按 not_found 抛出（不积回执）；结果只含提交时固化的 scope/schemaVersion/revision/payload，不声称 Task 重放/策略可执行/模型已登录。Work/Chat/基线等其余操作仍 unsupported，Host 路由仍未接入。

P02-2 / F-010 起新增 `query-service.ts`：QueryService 授权查询与快照/事件读取（P02-2 契约 §4/§7/§8/§9.3）——`listProjects`/`countProjectLabels`（project.read 能力核验先于筛选校验与任何读取，可见范围谓词经端口下推 SQL，P01 标签 any/all 与键集分页规则复用）、`getProject`/`getRepositoryBinding`（项目 + 绑定一次授权组装，无绑定 binding:null，不存在与不可见统一 forbidden）、`getGlobalSettings`/`getProjectSettings`/`getEffectiveSettings`/`exportGlobalSettings`/`exportProjectSettings`（全局读独立授权 settings.global.read，项目配置读 = project.read 或 settings.project.read；复用 P01 ConfigurationService 查询切片与 mergeEffectiveSettings 纯函数；缺失 not_found / configured:false 与损坏 corrupt_state 严格区分）、`getSnapshot`（ConsistentSnapshotStore 同一 SQLite 一致读视图：项目 + 绑定 + 当前配置 + 有效配置（含全局来源 revision）+ MAX(sequence) 水位 + readAt，禁止多次独立读取拼水位）与 `listEvents`（events.subscribe 授权；游标必填且经数据根/scope 绑定核验，坏游标 invalid_cursor 绝不当从零读取，未来游标合法；sequence 升序有界分页，eventId 供去重；行级可见过滤器防御复核）。principal 由可信装配显式传入，绝不从请求数据取身份；查询全部只读，不解析凭据、不执行脚本、不接受任意文件路径。Host 路由由 F-011 接线。

P02-2 / F-012 起同一 `query-service.ts` 补充 SSE 订阅切片（契约 §9.4）：`resolveEventResume`（建连恢复位置解析——events.read + 范围读能力授权先于任何读取；优先级 Last-Event-ID（在授权 scope 内解析为持久 sequence，未命中不区分不存在与跨 scope，invalid_input(unknown_event_id)）→ ?cursor=（decodeEventCursor 绑定数据根/scope，坏游标 invalid_cursor 绝不当从零读取）→ 缺省 400 cursor_required；未来游标合法，等待是订阅方策略；返回同位置不透明续读游标）与 `readEventBatch`（Host 可信传输面自持排他下界 + 1..500 有界分页；每次调用重新核验当前授权，能力/可见性撤销即拒绝；行级可见过滤器防御复核；映射失败（corrupt_state 等）不伪装成空流）。Host SSE Hub（F-012 runtime/sse-transport.ts）是唯一调用方；本切片不开 HTTP、不建内存事件工作流。

P03-6 / F-001 起新增 `runtime-execution.ts`：Runtime 执行会话服务（可信注册消费 + 适配器句柄契约包装）——start 前依次拒绝请求结构（validation）、配置能力目录不兼容（configuration）、未注册 runtime（missing_runtime）、描述符 provider/model 不一致（configuration）与权限/隔离不可落实（permission）；start 后逐项校验适配器产出（事件/结果/停止证据/取消回执），适配器非 RuntimeError 异常归为 process，契约违约为 protocol（未知终态 unknown_terminal 不伪造 failed）。eventsEnded/resultSettled/cancelAccepted/stopConfirmed 四项事实互相独立，result 由会话层自持有 Promise 只结算一次；未知公开事件保留有界受限诊断不透传 payload，事件序列必须严格递增、数量受请求政策上限约束。不做预算预占、不写业务库、不决定 Task 验收、不实现超时看门狗；只依赖 ports，不接触适配器/HTTP/SDK。

P03-6 / F-002 新增 `execution-input-binding.ts`：`createExecutionInputBindingService` 在当前 Attempt claim/workspace 及前序准备回执基础上绑定不可变执行输入，重核 Artifact 身份与必需正文，校验 acceptance、策略、权限、cwd/realpath、恢复来源和 RuntimeRequest；成功返回受限读取器与按 Attempt 关联的读取证据，拒绝路径尽力发布失败证据。读取器仅允许已绑定用途，逐次重核权威索引与正文，并执行次数、单项、总量和时限上限；不打开业务数据库句柄，不实现 ContextBuilder、原生恢复档案或完整 resume。

其余执行会话职责仍由 `runtime-execution.ts` 提供；F-002 只负责把不可变输入安全接到 RuntimeRequest，FakeRuntime 的声明式文件/工具执行、Session 持久化和结果结算由后续任务实现。

P03-6 / F-007 起新增 `work-evidence-recorder.ts`：`createWorkEvidenceRecorder` 最小有界公开事件与结果证据采集器——事件与结果同时接收（result 立即挂载观察，事件主循环可被结果结算唤醒进入有界尾部）；逐条 classify 并凭 eventIdentityPrefix 核验归属（外来事件仅留有界诊断不进水位）；稳定 eventId 去重（全等重投丢弃计数、身份冲突记缺口）、声明有限乱序窗口（超窗记 missing_sequences、窗口前迟到不持久化）；有界分块先经 Artifact 发布端口落盘 ready 后再以 activity 推进 Session recording_watermark（未持久不计入水位，缺口同步 ≤32 条）；脱敏在结构化序列化前递归处理（秘密字面量不进入正文），不解析凭据引用；尾部等待有界（result_tail_timeout/events_tail_timeout）；required 记录失败尽力取消句柄、标 recording_failed 缺口、发布 coverage='failed' 诚实清单并抛 WorkEvidenceRecordingError（safeStopRequired=true）阻止后继执行；清单 coverage complete 只对无缺口已声明范围成立。不推进 Session ended/stopped（F-009/F-010），不决定 Task 验收，不实现完整供应商 Recorder。
