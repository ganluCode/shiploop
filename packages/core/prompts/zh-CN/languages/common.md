## 通用开发规范

- 先核对现有实现、已完成工作、项目 AGENTS.md 和选定 Skill；复用仓库已有模式，不重复搭建已存在的能力。
- 一次只实现当前 Task；保持改动局部，不附带重构、升级依赖或生成无关文件。语言专属规则未知时沿用项目约定，不猜测新工具链。
- 按实际风险处理输入校验、错误传播、取消、资源释放和秘密脱敏；只有涉及共享资源或副作用时才设计锁、事务、幂等与恢复边界，不为空问题增加框架。
- Task 只运行当前改动相关的单元测试。不要运行项目全量、其他 Feature、Phase 或重量级集成验收；需要更大范围时记录原因交由 Core/负责人安排，不自行扩大范围。
- 失败先检索精确错误、受影响文件和有界日志，不扫描或内联全部 Session、历史报告、依赖目录。已有测试结果可复用时不要为获取同一段输出重复运行。
- 测试命令、退出码、范围、未执行项据实报告；保留用户改动，不弱化测试、不伪造通过。Git 正式提交、推送、审批和业务元数据由 Core 管理。

## 代码目录与模块组织

- 在现有架构分层内，尽量按业务模块、能力或稳定职责组织相关代码，让审查者能从目录和文件名判断用途，容易找到同一功能的实现、契约及相关测试。沿用项目约定，不为了分类打破层级、公开 API 或依赖方向。
- 把握目录粒度：不要把不同职责长期堆在一个难以浏览的平铺目录，也不要为每一两个文件机械创建目录、按 Task/Feature 编号建源码目录或增加多层空壳。优先内聚、命名清楚和适度层级，不设固定文件数量配额；小而明确的独立模块可以保留少量文件。
- 新增文件先判断是否属于已有模块；当目录已经难以快速定位职责时，才考虑按真实模块边界分组。共享代码有明确归属，避免把无关内容都放入 utils/common，也不要为了减少文件数合并不相关实现。
- 目录分类服务于人类查找和审查，不改变功能、权限或验收要求，不单独充当阻塞功能交付的数量门禁。当前 Task 只组织本次新增或必要修改的代码；已有目录的大范围迁移需单独安排，不能顺带整理、移动其他模块或扩大测试范围。

## TDD：红—绿—重构

新增功能、Bug 修复和可测试的行为变更遵循测试驱动开发；语言专属规范不能省略这个流程。

1. **核对现场**：先读现有实现、相关测试和上次执行证据。恢复或返工时保留已有代码及有效测试结果，针对未完成行为继续，不为了重演 TDD 删除已完成代码或用户改动。
2. **RED**：为当前最小行为先新增或调整相关单元测试，再运行该测试，确认它因预期行为缺失或缺陷而失败。导入错误、环境错误或错误断言不算有效红灯；测试直接通过时先核对行为是否已经实现，避免重复开发。
3. **GREEN**：只编写使该测试通过所需的最小实现，再运行同一测试。Bug 修复必须有能复现原问题的回归用例；不要先写完整实现、最后补测试来冒充 TDD。
4. **REFACTOR**：通过后仅整理当前变更需要的重复或结构问题，保持外部行为不变，运行受影响的相关单元测试确认仍通过；不顺带做无关重构。
5. **记录证据**：报告实际红灯原因、绿灯命令与结果、相关测试范围和未执行项。不虚构红灯；不通过删测试、降低断言、随意 skip 或扩大 mock 绕过真实行为。

每轮选择最小相关测试文件或用例，Task 收尾仅运行受影响单元测试集合，禁止因 TDD 默认追加全仓、Feature 全量或 Phase 集成验收。既有有效证据可复用；实现变化后必须重验受影响部分。

纯文档、无可执行行为的配置/格式调整，不为凑流程制造无意义单元测试，使用相应静态校验或内容核对并说明原因。需要真实外部服务或无法在当前授权内安全复现的行为，记录验证缺口和阻塞，不擅自调用服务、不声称已完成 TDD 验证。
